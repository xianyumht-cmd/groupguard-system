# NapCat GroupGuard 项目生产分析与完善建议

生成时间：2026-06-09

## 1. 项目定位

`onebot-plugin-groupguard` 是一个面向 SnowLuma/OneBot 11（兼容 NapCat）的群管插件，当前已经具备“群管理 + 风控 + 入群验证 + 互动积分 + 问答 + 授权 + WebUI + 动态命令”的完整产品雏形。

项目不是简单脚本型插件，已经有明显的工程化痕迹：

- `runtime` 负责消息/事件入口与 WebUI 路由。
- `commands/modules` 负责命令路由拆分。
- `services` 承载主要业务逻辑。
- `domain`、`app/use-cases`、`infrastructure` 正在向分层架构迁移。
- `storage_adapter` 使用 SQLite/WAL 承载核心数据。
- `action_queue_service` 对踢人、禁言、撤回、自撤回等高风险动作做限速、去重、重试和补偿。
- `dynamic-commands` 已具备插件化命令、熔断、指标和观测能力。

当前项目的主要挑战不是“功能不够”，而是功能已经足够多，生产环境会遇到状态一致性、权限边界、数据口径、外部接口可用性和可维护性问题。

## 2. 本次已完成的功能整改

### 2.1 为“入群欢迎”增加开关

新增群级配置项：

- `disableWelcome?: boolean`

支持通过已有功能开关命令控制：

- `开启功能 入群欢迎`
- `关闭功能 入群欢迎`

行为调整：

- 关闭入群欢迎后，未开启入群验证时不再发送欢迎语。
- 开启入群验证时，验证提示中不再拼接欢迎词。
- 默认值为开启欢迎，即 `disableWelcome: false`，兼容已有配置。

涉及文件：

- `src/types.ts`
- `src/config.ts`
- `src/runtime/runtime_event_pipeline.ts`
- `src/services/risk_service.ts`

### 2.2 为“邀请统计”增加重置数据能力

新增群内管理员命令：

- `重置邀请统计`
- `清空邀请统计`

执行后会同时清理：

- SQLite `invites` 表中当前群的数据。
- `data/invite_stats/<groupId>.json` 中当前群的邀请关系明细。
- 内存中的邀请统计缓存。

涉及文件：

- `src/services/interaction_service.ts`
- `src/commands/modules/interaction.ts`
- `src/services/invite_service.ts`
- `src/storage_adapter.ts`
- `src/db.ts`
- `src/repositories/groupguard_repository.ts`

### 2.3 修正邀请统计开关的数据记录口径

生产问题中提到“邀请统计不准确”。本次修正了一个明显口径问题：

原行为：

- `group_increase` 事件一来，先无条件写入 `invite_service` 的关系明细。
- 之后才判断 `disableInvite`，决定是否写入 SQLite 积分/邀请计数。

后果：

- `查邀请` / `查来源` 读取关系明细。
- `邀请查询` / `邀请榜` 读取 SQLite 统计。
- 当邀请统计关闭过、重开过、或数据迁移过，两边数据容易不一致。

现行为：

- 只有邀请统计开启时才记录邀请关系明细和 SQLite 统计。
- 新增重置命令会同时清理两套数据。
- SQLite 中邀请人记录会同步维护 `invitedUsers`，降低排行榜与明细口径差异。

## 3. 邀请统计不准确的生产原因分析

### 3.1 双数据源口径不一致

当前邀请功能有两套数据：

- SQLite `invites`：用于 `邀请查询`、`邀请榜`、邀请积分。
- `data/invite_stats/*.json`：用于 `查邀请<QQ>`、`查来源<QQ>`。

这两套数据以前不是完全同步，尤其是功能关闭、重启、重置、迁移后容易产生差异。

建议后续把邀请统计统一到 SQLite，`invite_service` 只保留兼容迁移或派生查询，不再作为主数据源。

### 3.2 operator_id 不一定等于真实邀请人

NapCat/OneBot 的 `group_increase.operator_id` 在不同入群场景下含义可能不同：

- 管理员同意入群申请时，operator 可能是管理员。
- 成员邀请入群时，operator 可能是邀请人。
- 自动审批、扫码入群、机器人自身入群等场景可能为空或不可靠。

因此，邀请统计不能只相信 `group_increase.operator_id`。

建议：

- 在 `request/group/add` 阶段记录 `flag/comment/sub_type/user_id`。
- 对邀请入群、管理员审批、自动审批分场景标注来源可信度。
- 统计展示时显示“可信邀请”“审批人”“未知来源”三类。

### 3.3 去重规则过于简单

当前逻辑以“被邀请人是否已有 inviterId/reverse 记录”为去重依据。用户退群后再次被不同人邀请，旧记录会阻止新记录生效。

建议：

- 引入邀请事件表，而不是只存当前映射。
- 字段包括：`group_id`、`inviter_id`、`invited_id`、`join_time`、`source_type`、`confidence`、`event_id`。
- 排行榜按时间窗口统计，例如本周、本月、全部。
- 对同一 invited_id 支持“最近一次有效邀请”。

### 3.4 邀请奖励和统计强绑定

当前邀请统计写入时会顺手给邀请人加积分。统计口径不准会直接导致积分不准。

建议：

- 邀请关系记录、邀请奖励发放、排行榜统计拆成三个步骤。
- 奖励发放记录单独落表，避免重复发奖。
- 支持管理员撤销一条邀请奖励。

## 4. 已有功能清单与完善建议

### 4.1 入群验证与欢迎

已有能力：

- 数学验证。
- 暗号验证。
- 自动审批。
- 私聊欢迎配置。
- 入群欢迎词。
- 黑名单入群拦截。

主要问题：

- 验证 session 只在内存中，插件重启后会丢失。
- 欢迎语、验证语、自动审批之间的行为边界以前不够清晰。
- 入群来源识别不足，影响邀请统计。

建议：

- 验证 session 持久化，重启后恢复倒计时。
- 增加“验证中用户列表”和手动通过/踢出命令。
- 入群欢迎、验证提示、私聊欢迎三类开关分开控制。
- 入群事件记录统一落库，供邀请统计、风控和审计复用。

### 4.2 邀请统计

已有能力：

- 邀请查询。
- 邀请榜。
- 查询某人邀请了谁。
- 查询某人来自谁邀请。
- 邀请奖励积分。

主要问题：

- 双数据源。
- operator_id 可信度不足。
- 退群/重进场景处理不完整。
- 缺少重置、修复、重算能力。

建议：

- 统一数据源到 SQLite。
- 增加 `重算邀请统计`：从邀请事件表重算排行榜。
- 增加 `撤销邀请 <被邀请QQ>`。
- 增加统计窗口：今日/本周/本月/全部。
- 展示数据可信度，避免把审批人误报成邀请人。

### 4.3 群管理

已有能力：

- 踢出、禁言、解禁。
- 全体禁言/解禁。
- 警告、清警告、查看警告。
- 头衔管理。
- 名片锁定。
- 黑白名单。

主要问题：

- 部分管理动作依赖实时权限查询，接口失败时用户感知不够清楚。
- 警告、积分、处罚之间的事务一致性仍需增强。
- 批量管理能力还不够完整。

建议：

- 所有管理动作输出统一 action id，便于追踪。
- 增加“处罚撤销”能力。
- 警告处罚、积分扣除、记录日志使用事务。
- 支持批量黑名单导入/导出。

### 4.4 风控与内容过滤

已有能力：

- 违禁词过滤。
- 拒绝词。
- 刷屏检测。
- 复读检测。
- 媒体类型屏蔽。
- 二维码检测。
- 自动风控收敛。
- 管理员/群主保护。

主要问题：

- 用户配置正则可能造成 ReDoS。
- 高风险动作虽有 ActionQueue，但普通发送链路仍需更统一的失败治理。
- 风险等级与功能降级矩阵还不够产品化。

建议：

- 正则预编译、长度限制、复杂度限制。
- 风控事件统一落库，支持 WebUI 回放。
- 增加 L0/L1/L2/L3 风险等级与自动降级策略。
- 违规命中记录提供“为什么处罚”的可解释输出。

### 4.5 问答系统

已有能力：

- 精确问答。
- 模糊问答。
- 正则问答。
- 问答冷却。
- 人格模板和场景模板。

主要问题：

- 正则风险。
- 问答列表较大时每条消息线性扫描。
- 回复模板质量和风控之间缺少量化指标。

建议：

- 精确问答使用 Map。
- 模糊问答建立关键词索引。
- 正则问答限制数量和复杂度。
- 问答命中、冷却、熔断统一进入观测指标。

### 4.6 互动、积分、签到、抽奖、商城

已有能力：

- 每日签到。
- 签到榜。
- 积分查询。
- 抽奖。
- 兑换免死金牌/头衔/解禁等。
- 活跃统计。

主要问题：

- 积分读改写不是完全原子，同一用户并发命令可能覆盖。
- 兑换中的事务封装存在异步回调风险。
- 积分来源和消费没有独立流水。

建议：

- 增加积分流水表。
- 签到使用唯一日期约束。
- 抽奖、兑换、邀请奖励统一走积分账本。
- WebUI 展示用户积分流水和异常修正入口。

### 4.7 防撤回与自撤回

已有能力：

- 防撤回聚合通知。
- 自身消息自动撤回。
- 撤回动作持久化补偿。
- 撤回去重、限速、重试。

主要问题：

- 撤回补偿依赖周期轮询，高峰时可能形成积压。
- 撤回失败原因需要更细分，例如权限不足、消息过期、接口失败。

建议：

- 增加撤回任务状态页。
- 按失败码区分是否重试。
- 对过期消息直接终止，不进入无效重试。

### 4.8 动态命令与外部接口

已有能力：

- HTTP 动态命令。
- 插件命令注册。
- 熔断、重试、指标、慢命令统计。

主要问题：

- HTTP URL 只校验协议，缺少内网/本机地址限制。
- WebUI 如果暴露，动态命令配置会带来 SSRF 风险。
- 外部接口返回解析规则仍需更强约束。

建议：

- 增加 URL allowlist。
- 默认禁止 localhost、内网、link-local、metadata 地址。
- 动态命令配置变更需要 owner 权限和审计日志。
- 输出结构增加 schema 校验。

### 4.9 WebUI 与运行时接口

已有能力：

- 配置读写。
- 群配置导入导出。
- 日志查看与清理。
- runtime 指标、插件指标、健康状态。
- 风险开关。

主要问题：

- 大量路由使用 `getNoAuth/postNoAuth`。
- 配置接口会返回敏感字段。
- 写配置不是原子写。

建议：

- 所有写接口加鉴权。
- 敏感字段脱敏，例如 token、授权码、主人 QQ。
- 保存配置使用临时文件 + rename。
- WebUI 操作写入审计日志。

### 4.10 存储与配置

已有能力：

- SQLite WAL。
- JSON 迁移。
- 分群配置存储。
- 部分任务持久化。

主要问题：

- 配置文件同步写但非原子。
- 内存缓存与 SQLite 容易产生口径差异。
- 部分事务封装不支持 async。

建议：

- 配置保存队列化、原子化。
- 所有统计主数据统一 SQLite。
- 缓存只做读取加速，写入后必须失效或同步刷新。
- 事务封装分为同步事务和异步事务，避免误用。

## 5. 生产优先级路线图

### P0：立即处理

- WebUI 写接口鉴权。
- 配置保存原子化。
- 邀请统计统一数据源。
- 验证 session 持久化。
- 积分/签到/抽奖原子化。
- 正则问答 ReDoS 防护。

### P1：稳定性增强

- 风控事件落库。
- 动作队列状态页。
- 外部接口 allowlist。
- 邀请统计可信度标记。
- 积分流水表。
- 日志脱敏。

### P2：产品化完善

- WebUI 增加邀请统计修复面板。
- 群配置版本与回滚。
- 风控等级自动降级矩阵。
- 动态命令市场/插件权限模型。
- 生产巡检报告和周报。

## 6. 建议补充的测试

- 关闭邀请统计后，新成员入群不写 SQLite，也不写关系明细。
- 重置邀请统计后，`邀请查询`、`邀请榜`、`查邀请QQ`、`查来源QQ` 都返回空。
- 开启/关闭入群欢迎后，未验证入群场景是否发送欢迎语。
- 开启验证且关闭欢迎时，验证提示不拼接欢迎词。
- 同一用户重复进群时不会重复给邀请人加分。
- 同一用户并发签到只成功一次。
- WebUI 未授权请求不能修改配置。

## 7. 结论

项目已经具备比较完整的群管产品能力，但生产稳定性的核心在于统一状态、统一权限、统一观测。

本次修复解决了两个明确需求：

- 入群欢迎可开关。
- 邀请统计可重置。

同时修正了邀请统计的一个实际不准确来源：邀请统计关闭时仍写入关系明细，导致不同查询命令读到不同口径。后续建议继续把邀请统计统一到 SQLite 事件表，并把积分奖励改成可审计的流水模型。
