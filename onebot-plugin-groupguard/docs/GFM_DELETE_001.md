# GFM-DELETE-001：群文件删除失败修复记录

## 问题

GroupFileMirror 在接收群上传新文件后，清理上一份文件时出现：

```text
delete_group_file:100:failed
```

该问题只属于群文件搬运模块，与查询迁移无关，不要求回滚当前查询版本。

## 根因

当前 SnowLuma/NapCat 链路中存在两种用途不同的文件标识：

1. `upload_group_file` 返回文件消息/上传链路中的原始文件 UUID；
2. `delete_group_file` 需要群文件系统列表返回的、可由 NapCat 解码的编码 `file_id`。

旧实现把上传返回的原始 UUID 直接保存为删除参数，导致 `delete_group_file` 无法解码该值并返回失败。

## 修复

- 上传成功后调用 `get_group_root_files`；非根目录规则调用 `get_group_files_by_folder`。
- 根据文件名、大小和上传时间窗口定位刚上传的目标文件。
- 分开保存：
  - `targetFileId`：上传/消息链路使用的原始 ID；
  - `targetDeleteFileId`：删除群文件使用的编码 ID；
  - `targetBusid`：群文件元数据中的业务 ID。
- 删除旧文件时只使用解析后的删除 ID。
- 兼容旧状态文件：缺少删除 ID 时，在清理前重新查询并安全补全。
- 同名候选不唯一或不在上传时间窗口内时，不猜测、不误删，保留待清理状态供后续重试。

## 回归验证

专项验证覆盖：

- 群文件列表返回结构解析；
- 秒级上传时间转换；
- 同名文件按上传时间选择正确对象；
- 时间窗口外的旧同名文件不会被选中；
- `busid` 被保留；
- 根目录和子目录查询动作均保留在正式实现中；
- 查询迁移代码不在本任务改动范围内。

## 生产验收

部署后连续搬运两份符合规则的新文件：

1. 第二份文件成功出现在接收群；
2. 第一份文件消息被撤回；
3. 第一份文件实体从接收群文件库删除；
4. 日志不再出现 `delete_group_file:100:failed`；
5. `group-file-mirror-state.json` 中待清理队列不持续增长。
