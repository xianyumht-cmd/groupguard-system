# Koishi 市场能力差异与后续参考

> 状态：已评估，暂缓实施  
> 记录日期：2026-07-28  
> 适用项目：GroupGuard（SnowLuma / OneBot）  
> 参考入口：https://koishi.chat/zh-CN/market/

## 1. 当前决定

现阶段不接入 Koishi，不安装 Koishi 市场插件，也不以 Koishi 插件为理由重构 GroupGuard。

GroupGuard 当前生产版本运行稳定。稳定性、现有客户行为兼容和商业授权链路优先级高于新增功能数量。

本文件仅保留市场调研结论、真实差异和未来启动条件，不代表当前开发任务，也不应进入近期版本排期。

## 2. 已确认的现有能力

GroupGuard 当前已经具备：

- 入群验证、自动审批、欢迎、退群拉黑；
- 违禁词、刷屏、复读、宵禁、媒体屏蔽、二维码检测；
- 撤回、禁言、踢出、拉黑、警告、名片锁定；
- ActionQueue、动作限速、去重、随机延迟、失败保护；
- 全局、分群、用户和查询维度的发送及查询限流；
- 商业授权、分群功能开关和权限判断；
- 自动问答、定时群消息、签到、积分、邀请统计；
- LOL 查询、骗子/同行查询、视频查询、ELE 等业务接口；
- HTTP 动态命令、参数映射、权限、分群范围、响应模板、超时、热重载；
- SnowLuma 独立运行链、配置备份、WebUI、风险分析和健康状态页面。

因此，Koishi 市场中的普通群管、通用限流、基础 Webhook 命令等插件，与现有能力高度重复。

## 3. 市场方向与 GroupGuard 的差异结论

| 市场方向 | GroupGuard 当前情况 | 结论 |
|---|---|---|
| 基础群管 | 已有完整验证、处罚、风控和权限链 | 不引入，不重写 |
| 通用限流 | 已有更细的队列、查询、用户、群和全局限制 | 不引入 |
| Webhook / HTTP 命令 | 已有成熟动态命令执行底座 | 仅参考配置体验 |
| 通用 Cron | 已有每日定时群消息，但不是通用调度器 | 暂无实际需求，不做 |
| 群管 WebUI | 已有较完整控制台 | 后续只补真实运营缺口 |
| 机器人账号管理 | 现有重点是管理群成员 | 未来可参考机器人生命周期闭环 |
| 群文件搬运 | 不属于现有核心群管链 | 必须独立验证和立项 |

## 4. 未来可能有价值的参考方向

### 4.1 机器人自身生命周期管理

可能包括：

- 收到群邀请；
- 机器人加入未授权群；
- 机器人被踢出群；
- 机器人被禁言或解除禁言；
- 机器人获得或失去管理员权限；
- QQ 账号切换；
- OneBot / SnowLuma 长时间断线；
- 主人手动审批群邀请或手动退出群。

该方向只有在实际出现以下问题时才重新启动：

- 经常被拉入未知群；
- 客户频繁反馈机器人被踢或失去权限而无法及时发现；
- 当前人工排查明显耗时；
- 需要商业化管理大量授权群。

未来启动时应先做只读事件采集，不得直接上线自动退群、自动拒绝或自动处罚策略。

### 4.2 主动健康告警

当前健康状态主要通过 WebUI 查看。未来可研究：

- 连续发送失败告警；
- 长时间未收到事件告警；
- WebSocket 重连异常告警；
- 账号变化告警；
- 外部查询接口连续失败告警；
- 同类异常冷却和去重。

只有当“不回复”排查成为持续维护成本时才实施。

### 4.3 动态命令配置体验

现有执行底座保留不动。未来最多增加可选配置能力：

- 成功状态码；
- 成功回复模板；
- 失败回复模板；
- 参数默认值；
- 参数候选值；
- 图形化新建、复制、测试和预览；
- JSON 高级编辑模式继续保留。

所有新字段必须可选，旧 `commands.json` 必须无需修改继续运行。

### 4.4 运营记录管理页

底层已有审计、风险和动作数据。未来可补只读管理页面：

- 警告记录；
- 黑名单来源；
- 撤回、禁言、踢出结果；
- 触发规则和证据；
- 失败原因；
- 按群号、QQ、时间和动作筛选；
- 导出排查报告。

修改警告或黑名单的功能必须晚于只读页面，并保留完整审计历史。

### 4.5 通用 Cron

当前不做。只有出现以下明确需求时再评估：

- 一次性定时任务；
- 多周期任务；
- 定时执行指定查询或动态命令；
- 服务离线后补执行；
- 需要统一管理多个内部定时器。

不得为了“框架完整”而额外引入调度系统。

### 4.6 群文件搬运

该能力与 Koishi 市场普通文件发送插件不同，目标链路可能包括：

1. 监听指定来源群的新群文件；
2. 获取文件标识、下载地址和元数据；
3. 下载并上传到指定接收群；
4. 记录来源文件与目标文件映射；
5. 来源侧删除或撤回旧文件时，按配置同步处理目标文件。

未来继续前必须先确认 SnowLuma / OneBot 实际提供：

- 群文件上传事件；
- 稳定的文件下载能力；
- 群文件上传动作；
- 群文件删除动作；
- 文件事件与普通消息撤回的区别。

在能力确认前，不得把该功能塞入现有消息处理主链。优先作为独立模块或独立服务验证。

## 5. 后续启动时的强制原则

未来任何人重新启动本文件中的方向时，必须遵守：

1. 不迁移 Koishi 生产宿主；
2. 不直接安装第三方市场插件到正式机器人；
3. 不重写现有 ActionQueue；
4. 不改变现有查询限流；
5. 不改变现有客户指令和配置含义；
6. 新功能默认关闭；
7. 先只读观察，再人工控制，最后才评估自动动作；
8. 必须通过现有 `npm test` 和 `npm run build:snowluma`；
9. 必须可独立回滚；
10. 必须在测试群和备用 QQ 验证后才能进入生产。

## 6. 当前优先级结论

- P0：维持当前稳定运行，不做相关改动；
- P1：无，当前没有需要立即实施的 Koishi 市场参考项；
- P2：出现真实维护成本后，再考虑生命周期告警和运营记录页；
- P3：动态命令图形化、通用 Cron；
- 独立立项：群文件搬运。

## 7. 当前停点

本次调研到此结束。

除非出现明确的新业务需求、持续故障或维护成本，不应根据本文件主动创建开发任务。
